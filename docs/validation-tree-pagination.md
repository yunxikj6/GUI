## InstaBox 实测

本机 Chromium 和标准 HTTP 启动器连接云机。临时仓库的根目录有 418 个文本文件，另有两个子目录。旧版列出了 400 个文本文件，未列出 `catalog`，因此也无法进入其中的 432 个文件。

- 新版从根目录打开了旧版遗漏的 `root-0400.txt`，再进入 `catalog`。在云机已返回第二页后拦下回执，工作台保留了前 400 个文件。点击重试发出了同一个游标。完整清单与两份按名排序的磁盘清单逐项一致，随后打开 `catalog/catalog-0431.txt`，读到了对应正文。
- 同一项目还有一个相对路径长 2,992 字节的目录。旧版工作进程返回 `too_large`。新版通过实际云机接口读完 410 个文件，每页分别为 81、81、81、81、81、5 项。最大的完整 JSON 响应为 251,372 字节。
- 新网页连接旧工作进程时显示旧版 400 项上限。已收到的文件可继续打开。
- 另在云机上创建名称含原始字节 FE 的子目录，放入 399 个短名文件、原始 FF 字节名文件和一个含合法 Unicode 替换字符的文件。浏览器可按显示名打开、编辑并保存原始字节文件，随后通过页尾游标取出另一个文件。在云机磁盘逐一核对，只有选中文件的正文发生了变化。

普通中文仍以 UTF-8 传输。无法解码的文件名字节在 JSON 中转义、在界面中显示为 `\xff` 等字样，字面反斜杠显示为 `\\`。本机回归还分别打开并保存字面名称含 `\xff`、含原始 FF、含 U+FFFD、含合法补充字符 U+10080 的四个文件，并检查各自的磁盘内容。[传输和浏览器回归](../tests/test_tree_transport.py)

## 分页规则和代价

每个目录先列子目录，再列普通文件。名称按 Unicode `casefold()` 排序，结果相同时按原名排序。翻页从上一页返回的最后一个排序键继续，因此删除该文件仍能继续。目录变动期间读取的是活动清单，刷新可以看到新加在游标之前的名称。游标绑定工作区和目录身份，文件系统提供创建时间时会纳入校验，以识别删除后立即复用的 inode。每页最多 400 项且整个响应不超过 256 KiB。[工作进程](../cloud/workspace.py) · [分页边界回归](../tests/test_tree_pages.py)

每次请求都会扫描当前目录，内存中保留排序最靠前的 401 个候选项。在实测的 Linux 文件系统上，读取 32,000 项目录的一页，对子项单独查询元数据 400 次。其他文件系统可能需要额外查询来确定文件类型。

| 短文件名目录 | 旧版第一页耗时中位数 | 新版第一页耗时中位数 | 新版读完整目录 |
| --- | ---: | ---: | --- |
| 8,000 项 | 61.93 ms | 70.85 ms | 20 个请求，1.43 秒，共 562,291 B |
| 32,000 项 | 60.50 ms | 84.99 ms | 80 个请求，7.55 秒，共 2,249,311 B |

这组测量走本机独立工作进程的标准输入入口，包含 Python 启动和序列化。两种大小的目录在新版首屏均发送 28,101 字节。另用 Chromium 连续点击加载并等待 8,000 项逐页显示，首次打开之后的 19 次追加合计 47.3 秒，最后一个文件可从树中打开。文件树保留已加载节点，32,000 项仅完成了工作进程的全量验证。[测量脚本](../experiments/tree_scan.py) · [逐次样本](measurements/tree-pagination.json)
