# 产品需求与验收

用户希望在本机打开一个图形工作区，像使用本机上的虚拟机一样使用云端 Linux。项目文件、应用进程和计算留在所选云机；能交给本机的文字、图片、代码差异和交互状态按需传过来。日常阅读和输入的清晰度、响应速度，以及网络恢复后能否接回工作，是判断产品好不好用的依据。

## 用户要求

| 要求 | 使用者应当能做到什么 |
| --- | --- |
| 一套连续的图形体验 | 打开客户端、选择云端项目、操作文件和应用、查看结果。日常工作通过图形控件完成，底层连接方式可随部署环境选择。 |
| 本地处理高频交互 | 用本机分辨率阅读文字和代码，使用中文输入法，选择、复制、滚动已收到的内容。图片按需传输。读取新数据、保存和执行由云端确认。 |
| 首批支持 Codex 和 Claude | 在同一项目里向编程助手提出问题或修改请求，看到进度、工具操作、结果和文件差异。用户要能判断请求是否已执行，并对需要授权的操作作出决定。 |
| 包含真正的 Linux 图形桌面 | 从工作区打开同一台云机上的原有图形程序，操作窗口、鼠标和键盘，直接检查程序对该项目产生的结果。 |
| 网络波动后还能继续工作 | 连接中断后能继续阅读已加载内容，恢复后找回任务及输出。重复提交不会重复执行，远端出现新文件版本时保留本地编辑。 |
| 能延伸到其他软件和云电脑 | 复用连接、项目、窗口入口、会话恢复等公共能力。根据软件可提供的数据选择专用前端、工具包接入或远程窗口显示。 |
| 长期独立开发 | 研究相关协议、实现和既有产品，写下选择依据；用原型、真实工作负载、故障复现和对照测量持续迭代。交付可运行的工程、源码及可复现的证据。 |

## 一条完整的验收路径

1. **打开云端项目。** 冷启动后打开一个文件和一张图片，放大界面、选择文字，再切回已查看的文件。观察哪些动作在本机完成。0.1 已实现文件树、文本与图片预览、有界内存缓存和后台版本校验。
2. **请助手处理项目。** 发送请求、读取输出，断开再连接。用 Codex 在当前成功回合追问，再刷新查看前后两轮。重复提交同一追问应找回已接受的任务。在两个标签页从相同回合提交不同追问，只能有一条成为下一轮。Claude Code 的验收路径为单轮只读问答。
3. **检查并修改结果。** 手动编辑已有文件，或让 Codex 为选定文本生成修改建议。检查建议时项目文件应保持原样。批准后，从 Git 差异核对改动。拒绝后，磁盘原文应保持完整。用第二个客户端先改动目标，再批准旧建议，检查前一份改动和待审差异是否都保留。
4. **打开 Linux 程序验证。** 0.1 在同一云机提供完整 Xfce 桌面，已验证接管输入、操作和交还。将单个原有程序呈现为独立本地窗口，是下一阶段的一条实验路线。
5. **验证恢复。** 分别测试客户端断网、页面刷新、云机挂起、云端进程终止。前两种情况下云机可以继续运行；实例挂起期间任务随之冻结；进程意外退出应当留下明确状态。已执行的实验及测量边界见[实机验收](validation.md)。

## 首版选择与后续选型

第一版使用本机 Python 启动器和浏览器承载图形界面，以 InstaBox 作为第一种云机后端，完整桌面使用 VNC。0.1 的性能验收集中在编程和桌面工具的典型操作。原生安装包、第二种云主机、逐窗转发和绘图引擎适配是后续候选；游戏、视频等高动态图形场景需要单独的工作负载与判断标准。

每轮比较应把本地输入及绘制、网络往返、云端执行、冷启动和恢复时间分开。已缓存文件的显示时间只回答其中一个问题。对于未适配的 Linux 程序，应在相同应用、分辨率和网络条件下比较画质、交互延迟及传输字节，再扩大支持范围。[技术路线与实验设计](technology-review.md) · [GTK 工具包实验](toolkit-experiment.md)
